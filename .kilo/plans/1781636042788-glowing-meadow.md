# Bug Investigation & Restocking Redesign Plan

## 1. Summary of Bugs Found

### Bug #1 (CRITICAL) — `createBranchGlAccounts` Never Creates Accounts
**File:** `app/Http/Controllers/Controller.php:246-264`
**Issue:** The condition `!isset($checkExistingGlAcct) || !empty($checkExistingGlAcct)` is always `false` for Laravel collections. `get()` never returns null, and `!empty([])` is always false. This means the code inside the `if` block **never executes**, so GL accounts and balances are never created when a new branch is set up.

### Bug #2 — Wrong `stock_id` in GL Transaction During Restock
**File:** `app/Http/Controllers/ProductController.php:476`
**Issue:** `"stock_id" => $stock->id` uses `$stock` which at line 446 was **reassigned** to a GlAccounts record (`$stock = GlAccounts::where('acct_no', $sgl)->first()`). It should use `$stocks->id` (the actual stocks table record from line 380). This breaks the link between GL transactions and stock movements.

### Bug #3 — No Null Check After Fetching Stock in `restock()`
**File:** `app/Http/Controllers/ProductController.php:380-381`
**Issue:** If no stock record exists for the product/branch, `$stocks` is null and subsequent property access (`$stocks->updated_by`) throws a null pointer exception. No error handling.

### Bug #4 — Product Model `stock()` Relationship is Inverted
**File:** `app/Models/Product.php:39-42`
**Issue:** Uses `return $this->belongsTo(stock::class, 'id', 'product_id')` but the `stocks` table holds `product_id`. Should be `return $this->hasOne(stock::class, 'product_id', 'id')` or `hasMany`.

### Bug #5 — OrderItem `stock()` References Wrong Class
**File:** `app/Models/OrderItem.php:24-27`
**Issue:** Uses `Stock::class` (capital S) but the actual model class is `stock` (lowercase). This causes a class-not-found error.

### Bug #6 — Inner Join Hides Accounts Without Balances
**File:** `app/Http/Controllers/GlAccountsController.php:50`
**Issue:** `INNER JOIN gl_balances K ON K.acct_no = G.acct_no` hides GL accounts that don't yet have balance entries. Should be `LEFT JOIN`.

### Bug #7 — Hardcoded Account Exclusion in Balance Sheet
**File:** `app/Http/Controllers/GlAccountsController.php:619`
**Issue:** `A.gl_no <> '1305001' AND A.gl_no <> '1307001'` hardcodes exclusions instead of checking account categories. Fragile design.

## 4. Restocking Redesign

### Current Behavior
- `stocks` table: **one record per product per branch**
- On restock: **updates** the existing record (overwrites purchase_price, selling_price, adds quantity)
- Result: Previous purchase/sale prices are **lost** from the current stock

### Desired Behavior
- Each stock acquisition (restock event) maintains its **own purchase_price and selling_price**
- Track remaining quantities at original prices (like inventory "lots" or "batches")
- When selling, apply FIFO (or configurable) stock deduction across batches

### Implementation Plan

**Option A: Stock Lots Table (Recommended)**
1. Create new migration `create_stock_lots_table`:
   - `id`, `product_id`, `branch_id`, `institution_id`
   - `purchase_price`, `selling_price` (original prices for this batch)
   - `quantity` (current remaining quantity in this batch)
   - `initial_quantity` (for reference)
   - `stock_date`, `manufactured_date`, `expiry_date`
   - `payment_method`, `status`
   - `created_by`, timestamps

2. **Phase 1 — Migrate existing data:**
   - Copy current `stocks` records into `stock_lots` (one lot per existing stock)
   - Keep `stocks` table as a summary view (or drop after validation)

3. **Phase 2 — Modify `restock()` in ProductController:**
   - Instead of updating existing stock, create a **new stock_lot** record
   - Post GL transactions referencing the new lot
   - Update the summary stock record quantity

4. **Phase 3 — Modify `newSale()` in OrderController:**
   - When deducting stock, use FIFO across stock_lots
   - Record which lot(s) each order item came from
   - Add `stock_lot_id` to `order_items` table

5. **Phase 4 — Update queries:**
   - Product list queries should aggregate across lots OR show latest price
   - Charts/reports should sum across lots

**Option B: Minimal Change — Add `stock_batches` alongside `stocks`**
1. Keep `stocks` as a summary (total quantity, latest prices)
2. Add `stock_batches` for detailed price tracking
3. Simpler migration, but dual-source data

### Recommendation
**Use Option A** (lots table) because:
- Cleaner data model
- Each acquisition truly has its own price
- FIFO tracking is natural
- Easier to audit and reconcile

## 5. Recommended Implementation Order

1. **Fix all 7 bugs first** (straightforward, non-breaking changes)
2. **Create stock_lots migration** (database change)
3. **Migrate data** (one-time script)
4. **Refactor `restock()`** to create new lots
5. **Refactor `newSale()`** to deduct from lots (FIFO)
6. **Update `order_items`** schema (add stock_lot_id)
7. **Update reporting queries** to work with lots
8. **Test end-to-end** with and without EFRIS enabled
